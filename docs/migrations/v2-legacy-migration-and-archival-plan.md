# MineCentral v2 legacy migration and archival plan

Date: 2026-09-24. Planning deliverable for [#21](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/21), under [epic #2](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/2).

Inputs: [v1 inventory](../audits/v1-feature-and-data-inventory.md), [product contract](../product/v2-product-requirements.md), and [route/navigation contract](../product/v2-information-architecture.md). Source baseline: `05c4456a230802b1c7b970f4a17e093209753652`. This plan does not run migrations, change production data, deploy redirects, or archive/delete files. Production schema, traffic, file inventory, providers, and backups remain unverified.

## Migration strategy and invariants

Use **additive schema changes, preservation in place, and staged application cutover**. Retain the existing PostgreSQL/auth/domain tables as the source of truth for maintained legacy features. Add new workspace, catalog, stack, configuration, and report objects alongside them. Physical relocation or replacement of legacy tables is not required for the first v2 beta; “migrate” can mean preserving their records and identity while changing the application around them.

Public listings are not managed workspaces. Do not create a workspace from every `serverTable` row, infer ownership of a running server, or copy publication state into workspace visibility. Existing resources may seed canonical catalog records through explicit mappings, but source identity, unpublished data, releases/files, and moderation state remain intact. No automatic merge on name, slug, or user email.

The initial rollout keeps one authoritative writer per data domain. Avoid an unimplemented dual-write scheme. A database move, auth-provider change, or destructive table consolidation requires a separate versioned migration with the copy protocol below; do not bundle it with navigation rollout. New v2 features can be disabled without deleting their saved records.

Preservation requirements:

- Keep original IDs and FK relationships wherever possible, including release/ticket numeric IDs and user/provider identity pairs. Record explicit old-to-new mappings when preservation is impossible.
- Keep drafts, pending/rejected resources, private messages, raw release download counters, vote timestamps/outcomes, and external customer/file references. UI aggregates are not the migration source.
- Preserve timestamp precision/timezone semantics and original text/unknown enum values. Do not fabricate missing dates, compatible versions, or delivery outcomes.
- Keep private data private in both application and archives. Credentials, database exports, logs, and user content are never stored in this Git repository.
- Importing records must not emit emails, create purchases, deliver Votifier rewards, increment downloads, or invoke upload callbacks as business actions.

## Execution owners and required evidence

Assign named people to these roles in a deployment-specific run record before execution. This document deliberately does not invent operator names, a migration date, retention policy, or production restore capability.

| Role                      | Responsibility / decision                                                                                                |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| Release owner             | Own cutover go/no-go, write reopening, known limitations, and abort decision                                             |
| Database operator         | Inspect live schema, capture/restore backup, run reviewed migrations, reconcile records and sequences                    |
| Application owner         | Deliver compatible release, access fixes, writer gating, route adapters and smoke checks                                 |
| Storage/integration owner | Inventory file bytes/provider references, drain callbacks and reward sends, reconcile external effects                   |
| Product/data owner        | Resolve ambiguous identity/duplicate mappings, archival retention, public URL exceptions, and any destructive retirement |

Keep a protected run record containing: source/target code SHAs, migration file hashes, actual schema version, flags/config versions (no secret values), backup IDs and restore evidence, table/file counts and checksums, mapping/quarantine totals, write-barrier time, callback/delivery drain results, validation results, operators, final decision, and rollback evidence. Store only a sanitized summary and artifact identifiers in the repository or issue tracker.

Execution gates: a tested restore point must cover the final pre-cutover state; reconciliation must show **zero unexplained missing rows/files, broken FKs, or identity collisions**; there must be **zero unresolved critical/high access or data-loss defects on enabled paths**. Define an acceptable outage window, measured restore time, and recovery objectives in the run record before scheduling. If the rehearsed operation exceeds that window or objectives, stop and redesign the cutover. Closing #21 does not mean these execution gates have passed.

## Ordered migration phases

| Phase                                | Actions                                                                                                                                                                                                 | Exit evidence / abort behavior                                                                                                                                                   |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| M0 — Discover deployment             | Inspect deployed commit, actual schema/indexes/FKs, all writers, provider apps/webhooks, file storage, scheduled jobs, row counts/status distributions, and URL traffic/index exports                   | Record drift from #18. Stop on unknown writers, missing backups, or unowned integrations; no production writes in this phase                                                     |
| M1 — Capture and rehearse            | Back up DB/schema/roles/sequences and referenced file bytes; record protected provider configuration; restore into an isolated environment with outbound side effects disabled                          | Prove restore, login identity mapping using test accounts, file access, and counts. Repeat the full planned cutover/abort on a copy; no production release until it passes       |
| M2 — Make the application compatible | Fix enabled-path auth/download defects from #18; implement deployment flags, explicit migration/write gating, callback idempotency/reconciliation, and old/new route adapters                           | Guest/owner/other-owner/admin checks pass. Retain an independently deployable compatible fallback release with the fixes; never roll back to known authorization vulnerabilities |
| M3 — Expand schema                   | Introduce reviewed versioned additive migrations under the workflow from #25; add new tables/indexes/mapping records without dropping or renaming legacy columns                                        | Old maintained features and new release both run against expanded schema. Confirm migration lock/runtime behavior on representative data; a failed migration stops the sequence  |
| M4 — Backfill / map                  | Execute the table order below for any actual copy; seed canonical identities only from approved mappings. Run idempotent batches and reconcile ambiguous records without exposing them as valid matches | Repeat the run without creating duplicates; verify row/field/file reconciliation. No navigation switch while unexplained differences remain                                      |
| M5 — Final write barrier             | Block new mutations, drain accepted in-flight writes and side effects, capture final DB/files state, apply final delta if copying, and rerun reconciliation                                             | All writers accounted for and paused; outstanding callbacks durably retained or completed. If drain cannot be proven, abort before switching authority                           |
| M6 — Switch application/routes       | Deploy compatible v2 with new features initially controlled by flags; activate route families only when their destinations/data are verified; rebuild caches and smoke-test before reopening writes     | Guest/owner/admin, retained URLs, sign-in, downloads and callbacks pass. Roll back application/flags while writes remain closed if any critical check fails                      |
| M7 — Observe and promote             | Reopen writes once, watch writes/errors/auth failures/downloads/callback backlog, validate canary records; activate more features gradually                                                             | Release owner confirms stability over the documented observation window; use rollback protocol if new-data or compatibility failures arise                                       |
| M8 — Archive and later contract      | Archive superseded code/docs with provenance; consider physical table/file/credential removal only in a separately reviewed destructive change                                                          | Retention, consumer absence, recovery, and final verification gates below must pass. No schema contraction during the initial cutover                                            |

The write barrier is an implementation requirement, not an existing repository feature. It must cover server actions, API writes, admin writes, auth callbacks/session writes if copying auth tables, UploadThing completion handlers, download counter increments, anonymous votes and reward delivery, metadata jobs, and any discovered external writer. A read-only UI or load-balancer flag alone is insufficient.

Prefer a short measured maintenance barrier plus a final consistent snapshot for a physical copy. An online alternative requires verified change capture that includes updates and deletions, a replay watermark, and exactly-once/idempotent application semantics; do not use `updatedAt` polling as a substitute. The audit shows timestamps are not reliably maintained everywhere, and `customer` has no primary key. No online move is approved by this plan.

## Data order and per-table treatment

The order below is the load order for a restore/copy and the preservation checklist for in-place rollout. New v2 tables have conceptual names here; their concrete schema/migration names are owned by their implementation issues. [Current schema exports](../../src/lib/db/schema.ts) are the evidence for the 14 legacy physical tables.

| Order | Physical table                        | First-cutover treatment and validation                                                                                                                                                                                                    |
| ----- | ------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | `user`                                | Retain IDs, unique emails, verification state, profile fields, roles, bans and timestamps. Resolve duplicate/invalid destination identities without silent merges; test banned-account behavior                                           |
| 2     | `account`                             | Retain user FK and provider/account identity pairs, token expiry metadata, and protected credentials. Never reconnect by email alone; use existing provider configuration unless an explicit auth migration is rehearsed                  |
| 2     | `verification`                        | Retain in place with compatible auth. If moving/changing auth semantics, expire/reissue pending verifications intentionally and document user impact; never accept old tokens under incompatible rules                                    |
| 3     | `session`                             | Preserve compatible sessions only when schema, secret, cookie/domain, and auth semantics are unchanged and tested. Otherwise invalidate deliberately and require login; preserve user/account records. Copy only under auth write barrier |
| 4     | `resourceTable`                       | Retain owner, slug, type, text, tags, links, images, status and timestamps. Audit case-folded slug collisions separately from database uniqueness; drafts are not made public catalog entries                                             |
| 4     | `serverTable`                         | Retain public-listing identity/address/owner, draft/published state, profile/banner, links, cooldown and timestamps. Do not auto-create workspaces; check lower(slug) and lower(address)+port uniqueness                                  |
| 4     | `ticket`                              | Retain ticket IDs, owner, title/category/status and date-only creation; don't invent time-of-day values                                                                                                                                   |
| 5     | `resourceTableReleases`               | Load after resource parents; preserve identity integers, `pluginId`, version/compatibility metadata, file URL, counters and timestamps. Validate release ID download resolution and actual bytes                                          |
| 5     | `liked_resources`                     | Load after users/resources; preserve composite pairs and timestamps; reconcile exact pair sets, not only totals                                                                                                                           |
| 5     | `serverVotifierTable`                 | Load after listings; preserve one-to-one server FK, enabled state, host/port/public key. Never send rewards as part of migration                                                                                                          |
| 5     | `serverVote`                          | Load after listing/user parents; preserve vote IDs, timestamps, optional user attribution, anonymous IDs/hashes, username, enabled snapshot and delivery outcomes. Don't replay failed/unknown historic deliveries                        |
| 5     | `ticketMessage`                       | Load after ticket/user parents; preserve message IDs, text, authors and precise timestamps/order                                                                                                                                          |
| 6     | `recentActivity`                      | Load after users; preserve IDs, verbatim free text and timestamps. Don't parse ambiguous strings into invented structured audit events                                                                                                    |
| 6     | `customer`                            | Load after users; preserve all three service customer IDs and row multiplicity. Reconcile duplicate rows and provider references explicitly; no silent upsert by user ID where source uniqueness does not exist                           |
| 7     | New catalog and mapping records       | Seed canonical project → source alias → version → provenance/evidence relationships; record every retained legacy resource/release mapping. Ambiguous matches remain separate/manual; no private metadata exposure                        |
| 8     | New workspace domain                  | Create workspace → stack entries → configs/revisions → evaluations/diagnostic sessions under new schema contracts; initially empty unless user action or explicit import creates them. Do not invent live observations                    |
| 9     | Sequences, constraints, derived state | Restore integer identity sequence state above imported IDs; validate FKs/uniqueness, compare raw preserved fields, then rebuild caches/search/derived counts from authorized source data                                                  |

For copied tables, manifest each source key, target key, transform version and disposition. For `customer`, preserve a snapshot-scoped row ordinal plus field checksum until a reviewed destination key exists; PostgreSQL physical row location is not a durable cross-database identity. Separate ambiguous records into a protected reconciliation ledger retaining all original values; unresolved user-owned records block enabling their affected feature rather than being dropped as “bad rows.”

### Files, identities, and side effects

Inventory every release binary, icon and banner referenced by the DB, including unpublished projects. Record stable storage key when available, current URL, owning record, byte size, checksum and backup destination in protected storage. If URL-only records cannot be resolved to provider keys, establish the mapping before cleanup. Compare file bytes to the final DB snapshot and account for in-flight uploads; don't call a URL manifest a file backup. Preserve old URLs/provider storage until replacement URLs or durable forwarding have been verified. Provider avatars may remain external references; record their availability limitations without assuming ownership of those files.

For UploadThing, stop new upload initiation before the barrier, keep verified callbacks available to finish or durably capture them, drain/reconcile uploaded objects without committed rows, and deduplicate completion handling by stable upload identity. Inspect actual provider retry behavior during implementation. Do not acknowledge and discard callbacks, delete unmatched files before reconciliation, or assume the source callbacks already provide idempotency.

Freeze new votes and drain in-flight TCP delivery before snapshot. A DB restore cannot undo a reward already delivered to a Minecraft server. Preserve the post-snapshot vote/delivery ledger separately during any recovery and mark uncertain deliveries for reconciliation; do not resend them automatically. Preserve cookie name/domain behavior and recent vote identities during cutover so migration does not reset cooldowns. Changing identity/retention policy is a separate reviewed operation.

Preserve OAuth client registrations, callback URLs and linked identities. Restore code/config coherently; changed secrets may require reauthentication. Don't copy secrets into a migration report. Reconcile any actual Stripe subscriptions/customer state with the provider before archiving billing code; restoring PostgreSQL does not reverse charges, cancellations, webhook effects or external subscription state.

Six authenticated page aliases become permanent only after their targets work: `/dashboard` → `/servers`; `/dashboard/account` → `/account`; `/dashboard/account/settings` → `/account/settings`; `/dashboard/tickets` → `/support/tickets`; `/dashboard/tickets/create` → `/support/tickets/create`; `/dashboard/tickets/[ticketId]` → `/support/tickets/[ticketId]`. Retain ticket IDs and access policy. All remaining private placeholder retirement/maintained editor decisions are in the manifest.

Rollout policy for those aliases: test in staging, enable **307 with `Cache-Control: no-store`** for the production observation window, then promote to the **308 steady-state decision from #20**. Remove `/account`'s existing reverse redirect in the same release as the new account page. Keep the new destinations in the fallback release: a browser-cached permanent redirect cannot be reliably recalled by reverting the server or purging a CDN. Temporary rollout is not a change to the final route map.

Keep host/domain stable during this migration. Preserve only destination-supported query parameters; drop transient toast/auth data and reject external return URLs. Test trailing slash, encoded slug, unknown ID, guest/owner/admin and GET/POST behavior. Don't redirect mutation methods to unrelated handlers. Keep canonical/sitemap entries for published retained content, remove retired placeholders, exclude private/draft pages, and monitor real indexed/inbound URL exceptions after deployment. Auth controls, not robots rules, protect private data.

## Rollback and recovery

Rollback is a prepared application/data operation, not an unconditional database restore. Decide based on whether new writes have been admitted and whether schema contraction has occurred.

| Failure point                                    | Response                                                                                                                                                                       | Required recovery evidence                                                                                                                                                          |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Additive migration/backfill fails before cutover | Stop at failed batch; disable new feature flags; retain legacy authority. Revert application changes if needed, leaving safe unused additive schema in place                   | Old maintained paths still work; record failed migration/batch state; never rerun unknown partial work without checking idempotency                                                 |
| Smoke check fails with writes still paused       | Switch back to the rehearsed compatible fallback release/config and route flags, rebuild affected caches, then re-open legacy writers                                          | Auth, files, records and APIs match the frozen baseline; new destination adapters remain for redirect compatibility                                                                 |
| Defect found after v2 writes resume              | Close affected writers; retain a fresh backup and all post-cutover data; disable affected v2 features and use fallback release on the expanded schema                          | Account for every admitted legacy/v2 write. New workspace/config/report records remain stored even if temporarily inaccessible; do not overwrite the database with the old snapshot |
| Data corruption requires restore                 | Freeze all writers; restore to an isolated recovery DB, then reconcile final-snapshot and post-snapshot inserts/updates/deletes from verified change evidence before promotion | Prove no acknowledged user change is silently lost. If recovery evidence cannot reproduce updates/deletions, stay in maintenance and escalate rather than claim lossless rollback   |
| External effects diverge                         | Stop delivery/billing/upload consumers as appropriate; reconcile provider records and protected event ledgers independently                                                    | Record delivered/unknown votes, new file objects and provider-side changes. No automatic reward replay or billing compensation based solely on restored DB state                    |
| Cached 308/retirement response persists          | Serve compatible destination routes and meaningful retired-page responses from fallback release; purge controllable CDN caches                                                 | Clients following cached new URLs still have working authorized destinations; do not depend on clearing every browser cache                                                         |
| Later destructive contraction fails              | Restore affected tables/files from the verified pre-contraction archive into isolation, apply intervening changes, verify mappings, then switch readers/writers                | Recovery exercised before destruction, including dependent children and file bytes; no blind reverse-order delete/DDL script                                                        |

Restore jobs run with provider-side effects disabled. Only after reconciliation may a designated owner reopen authoritative writers. If an auth secret/credential has been rotated or revoked, restoration must not reactivate an unsafe old secret; use the current secure configuration and require reauthentication where needed. Preserve relevant audit evidence through recovery.

### Reversible versus destructive operations

| Operation                                                                        | Classification                                                    | Conditions                                                                                                                                               |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Add unused tables/nullable fields and flags                                      | Normally reversible at application level                          | Keep old readers compatible; review lock/load effects and backups before DDL                                                                             |
| Backfill into separate tables with immutable mapping                             | Reversible while legacy data remains authoritative                | Preserve originals and run IDs; no side effects; cleanup only confirmed backfill-owned rows with no subsequent user edits                                |
| Navigation change and temporary 307                                              | Reversible with compatible targets                                | Ship flags/adapters and test both directions                                                                                                             |
| Permanent 308 or indexed-page 410                                                | Not fully reversible through server configuration alone           | Delay permanent promotion until observation passes; retain destinations and account for client/search caches                                             |
| Archive code/docs in Git with recorded provenance                                | Reversible for source                                             | Preserve commit/tag/manifest and runnable dependency/build context; source history alone does not restore data                                           |
| Session invalidation / verification expiry                                       | Intentionally user-visible and not undone by application rollback | Document reauthentication/reissue path; preserve account identity                                                                                        |
| Merge identities, rewrite IDs/slugs, normalize/drop fields, alter auth semantics | Potentially destructive                                           | Separate reviewed mapping with full original values, collision resolution and restoration proof                                                          |
| Delete parent rows, drop tables, remove release files or expire backups          | Destructive                                                       | Account for cascading votes/likes and non-cascading releases/messages; retain verified dependencies/bytes and defined retention decision before deletion |
| Revoke provider credentials or delete provider resources                         | Externally destructive                                            | Inventory consumers, replacement access and provider recovery constraints; database restore cannot reverse it                                            |

## Archival strategy

Separate source archival from user-data retention. “Archive” in #18 is a recommended disposition, not permission to remove active code or data immediately.

| Material                                                     | Planned treatment                                                                                                                                                                                                                                                                        | Prerequisite                                                                                                                              |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| Obsolete source and placeholders                             | Create a protected pre-v2 Git tag and sanitized archive index recording original paths, last working commit, replacement, reason, restore/build instructions, and removal PR. Remove unused runtime files through normal reviewed commits; don't keep executable copies under app routes | Prove no imports, navigation, direct consumers, callbacks or deployment configuration still depend on the code                            |
| Earlier server-list wayfinder docs and todo notes            | Preserve original files/history; add a dated historical-status pointer to the v1 audit and v2 contracts. If moved later, use `docs/archive/v1/` with old-path pointer documents to avoid breaking links                                                                                  | Archive manifest lists original/new paths and superseding documents; don't rewrite historical decisions as if they described current code |
| V1 audit and v2 decision documents                           | Keep as dated evidence under current paths                                                                                                                                                                                                                                               | Update with clearly dated amendments when reality changes; do not replace the source baseline silently                                    |
| Legacy resource/server-list/ticket code                      | Keep active during first cutover; archive only after maintained flows have replacements or an explicit retirement decision                                                                                                                                                               | User data/URLs remain accessible under the agreed contracts; schema references are not removed prematurely                                |
| Stripe/hosting helpers and unused detector/webhook code      | Archive source only after runtime/provider/environment consumer inventory; keep protected external-reference records                                                                                                                                                                     | Confirm actual billing/provisioning/webhook use rather than infer non-use from missing UI                                                 |
| Database exports, mappings, file bytes and provider metadata | Encrypted, access-controlled operational storage with owner, checksum, restore instructions, capture time and expiry policy                                                                                                                                                              | Tested restore and approved data-category retention/deletion policy; never commit secrets or private content                              |
| Build/release artifacts                                      | Retain last compatible application artifact plus lockfile, migration/config versions, deployment recipe and secret-reference names                                                                                                                                                       | Demonstrate deployment against expanded schema with secure current configuration                                                          |

Archive data must have a defined retention owner and expiry review, not indefinite storage by default. Before M8, record policy for account/provider credentials, private configs/logs, support history, vote identifiers, binaries, billing references, and backups; reconcile export/deletion requests with archives. Restore procedures must reapply the protected deletion/suppression ledger so backups do not silently resurrect previously deleted personal records. No automatic expiry job or destructive cleanup is introduced by this planning issue.

Destructive retirement requires all of: a named owner/approved retention decision, verified replacement/consumer inventory, reconciled row/file/mapping evidence, tested recovery of parents and dependents, an observation window chosen in the run record, a maintenance/rollback procedure, and a separately reviewable change. If any condition is unknown, retain the legacy object and defer retirement.

## Validation and release handoff

### Rehearsal checks required before implementation cutover

- Compare live schema to source: tables, columns, types, defaults, FKs/delete actions, indexes, sequences and any external job tables not present in Git. Source-only table count is not proof of production coverage.
- Compare row counts and deterministic field checksums by owner/type/status and key sets; validate no orphaned children, case-folded slug/address collisions, duplicate source aliases, lost `customer` row multiplicity, altered timestamps or missing unpublished records. Preserve counter values before deriving corrected displays.
- Validate resource-release bytes, icon/banner references, old URLs, specific numeric release downloads and unpublished visibility. Distinguish reachable URL from verified backed-up bytes.
- Exercise guest, owner A, owner B and admin across reads, server actions, APIs, upload completion and ticket replies. Test banned accounts and OAuth callback continuity with dedicated test identities.
- Verify vote cooldown continuity, no reward replay during backfill/restore, callback idempotency and reconciliation of accepted-but-incomplete uploads. Disable real side effects in rehearsals.
- Execute every route-manifest rule with a concrete fixture for each dynamic family, including encoded IDs/slugs and missing/private objects; ensure no account redirect loop, no workspace/listing identity confusion, and no API POST redirected to a page.
- Rehearse abort both before and after admitting representative new writes, including deletes, changes to existing rows, new v2 configs and external-event records. Restore to isolation and demonstrate preservation before declaring rollback ready.

### Unknowns and blocking conditions for deployment

No production connection or execution was attempted for #21. M0 must establish: actual schema/deployed version; data volume and downtime tolerance; all direct DB/API/provider writers; storage ownership and backup access; whether billing or hosting is active externally; actual indexed/historical URLs; auth/cookie compatibility; upload retry semantics; and retention/recovery objectives. Assign each uncertainty an operator and evidence before scheduling. These unknowns block deployment or destructive cleanup, not completion of this written plan.

Subsequent implementation depends on the schema workflow (#25), auth/authorization/platform work, feature schema/ingestion work, and reliability/security/privacy/launch gates described by #19. Don't run the existing `db:push` script as a production migration procedure. Define reviewed migration files and execution/recovery commands against the actual environment in the implementing issue; this plan intentionally contains no unverified production SQL or deletion commands.
