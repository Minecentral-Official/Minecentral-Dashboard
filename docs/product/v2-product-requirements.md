# MineCentral v2 product requirements and non-goals

Date: 2026-09-24. Status: proposed product contract for review; implementation is not complete.

Addresses [#19](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/19), under [product direction epic #2](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/2). Input: the [v1 inventory](../audits/v1-feature-and-data-inventory.md) and all 16 roadmap epics (#2–#17). Roadmap intent is distinguished below from proposed release boundaries; issue priority alone is not an MVP commitment.

## Product promise

MineCentral helps a Minecraft server owner **assemble, configure, troubleshoot, and maintain a working server stack**. The central experience starts with the owner's server workspace and the exact software/configuration they intend to run. Discovery supports choosing components for that server. Compatibility and diagnostic claims explain their evidence and limitations.

A successful core workflow ends with a saved, understandable stack, validated configuration files the owner can export, and an actionable explanation of known problems or upgrade risks. Saving a plan in MineCentral does not imply that a running server has been changed or observed.

The initial audience is a solo owner or a small community administrator managing their own server. Detailed personas and measurable journeys belong to [#22](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/22). Multi-server ownership is required; team administration and fleet orchestration are separate capabilities.

## Product objects and invariants

These are conceptual contracts, not a database schema or final route map.

| Object                      | Meaning                                                                                                           | Required distinction                                                                                 |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| Server workspace            | An owner-controlled record of a server's identity, selected platform, Minecraft/Java versions, and intended setup | Private by default; independent of a public server listing; creating one does not provision hosting  |
| Catalog project and version | Canonical software identity and a particular release, linked to original source IDs/URLs                          | Preserve provenance; similarly named projects from different sources are not automatically identical |
| Stack entry                 | A project's selected version and desired state in a workspace                                                     | Unknown/manual versions are representable; desired state is distinct from observed installation      |
| Configuration and revision  | A workspace's text configuration, optionally associated with a stack entry, plus immutable saved revisions        | Private content; an editor schema is guidance for a particular software version, not the file itself |
| Compatibility finding       | A conclusion about a precise project/version and target environment, with evidence and evaluation time            | Unknown is neither compatible nor incompatible; contradictory evidence is visible                    |
| Upgrade evaluation          | A recorded comparison of a source stack snapshot against a selected target                                        | Recompute creates a new evaluation; historical findings do not silently change                       |
| Diagnostic session          | Submitted log/artifact context, sanitized evidence, findings, and retention state                                 | User-submitted evidence is distinct from inferred causes; no implied live server access              |
| Public config / recipe      | Deliberately published reusable configuration or stack instructions, with attribution and versions                | Separate public objects; saving a private workspace never publishes its contents                     |
| Agent observation           | Explicitly opted-in metadata from an attached server                                                              | Separate from user intent; stale observations must not masquerade as current health                  |

## Non-goals

- Competing primarily on the number of hosted plugin binaries, download rankings, or public server votes. Existing records and URLs still require preservation decisions under PR-01.
- Becoming a Minecraft hosting provider, provisioning infrastructure, selling game servers, or replacing a hosting control panel.
- Claiming universal Minecraft/plugin support, guaranteed compatibility, or guaranteed root-cause detection. Unsupported and unknown inputs remain explicit.
- Automatically executing arbitrary uploaded JARs, scripts, or configuration snippets as part of catalog ingestion or diagnostics.
- Automatically modifying, restarting, upgrading, or rolling back a live server in the initial release. Exported files and proposed changes remain under owner control.
- Publishing private stacks, configs, logs, IPs, or credentials as a side effect of saving/importing them.
- Treating AI-generated explanations as compatibility evidence or making an AI subscription a prerequisite for the core workflow.
- Rebuilding legacy empty pages merely because their routes already exist.

## Legacy product boundaries

The [audit](../audits/v1-feature-and-data-inventory.md) remains the evidence source for what exists today. Workspace/stack/config/diagnostic objects are new capabilities; legacy `serverTable` records describe public listings and must not silently become connected, managed servers. Existing uploaded resources may seed catalog metadata only through an explicit provenance/identity mapping, retaining release IDs and files.

Public listing/vote and resource-directory capabilities enter maintenance/migration scope, not new feature expansion in the initial release. This document does not decide to shut down existing endpoints or discard their records. [#20](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/20) defines public/authenticated navigation and per-route behavior; [#21](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/21) defines migration order, redirects, archives, and rollback. Ticket history and account/provider links survive even if their presentation changes. Existing authorization and download-contract defects must be resolved before those paths are reused or exposed through v2.

## Proposed MVP: a focused owner beta

The proposed first release delivers the complete assemble → configure → troubleshoot → maintain loop for a bounded supported environment. This release cut is a planning assumption, not a claim that stakeholders have already approved deferring existing P0 issues. Broader capabilities remain requirements in the roadmap and are explicitly scheduled below.

Initial support target: **Java Edition, Paper plugin stacks**. This is a proposed support boundary rather than a verified compatibility claim. Platform/game/Java versions must come from an explicitly maintained, fixture-tested support matrix; do not advertise “all versions” or silently substitute the latest release. Velocity, other server platforms, modded stacks, and Bedrock-specific configuration support can retain metadata but are not promised end-to-end support in this beta. Existing legacy records for those targets are preserved. Exact supported versions must be selected and documented before inviting users.

| Catalog and assembly — PR-04, PR-05                | Source-agnostic project/version model, selected Modrinth and Hangar project metadata, manual/unresolved entries, conservative identity mapping; add/remove/select versions and persist stack | Comprehensive marketplace crawling, new binary-hosting business, automatic JAR installation                   |

A file syntax check does not establish plugin-specific semantic correctness. When a versioned config schema is unavailable, label validation as syntax-only. Keep temporarily invalid edits available for correction without replacing the last valid saved revision. Diagnostics must disclose that redaction cannot guarantee every secret was recognized and allow the owner to review submitted content. Choose and enforce text size, parser resource, and retention limits before releasing those features; arbitrary uploads are not part of this contract.

### End-to-end MVP acceptance scenarios

Each scenario is a release demonstration, not just a page or database table existing. Supported inputs and fixtures must be versioned so results are reproducible.

1. **Assemble:** a new owner signs in, creates a supported workspace, selects at least two catalog plugins with versions, adds an unresolved manual entry, reloads, and sees all entries unchanged. Required dependencies and the manual entry's unknown status are explained. A second account cannot retrieve or mutate the workspace through a direct URL/API/action.
2. **Configure:** import a representative YAML file containing an unknown key and comments, edit a value, save a revision, export/reparse it, and verify semantic values and the unknown key survived. Show any formatting limitations. An invalid edit retains recoverable text and the prior valid revision; restoring that revision produces the expected content.
3. **Troubleshoot:** submit a known-failure text fixture, review redaction, and receive a finding with sanitized evidence, relevant stack context, and an actionable next step. Unrecognized input is retained only under the stated policy and produces an honest insufficient-evidence outcome. Delete the session and verify documented deletion behavior.
4. **Maintain:** compare the recorded stack with a supported target; every entry gets a reasoned readiness state, and unknowns block an unqualified “ready” conclusion. The original stack is unchanged. Revisit the saved report after metadata refresh and confirm its source snapshot/findings remain intact.
5. **Recover and operate:** rehearse migration/restore on a copy, verify preserved ownership/files/links, and demonstrate that a failed source sync leaves saved user work usable with visible freshness/error state. Critical authorization and destructive-data findings for enabled paths are resolved before beta access.

[#22](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/22) should turn these scenarios into persona-specific journeys and pilot measures. Track first useful stack result, successful config export, diagnostic action usefulness, and upgrade-report completion using event metadata rather than private payloads. Do not claim adoption, accuracy, or time-saving targets have been achieved before a pilot measures them.

### Dependency reconciliation needed before scheduling

The current issue graph describes a broader v2 release than this proposed beta. Preserve existing issue requirements until a reviewed issue split or dependency update makes the scope explicit:

- [#69](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/69), [#77](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/77), [#85](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/85), and [#108](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/108) are P0 foundations for proposed later features. Calling the beta an MVP does not by itself resolve these P0s.
- [#117](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/117) depends on public configs and recipes. The beta needs catalog/help discovery without pretending the full unified index is complete. [#123](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/123) likewise depends on the broader public knowledge surface; private-route exclusion still applies from day one.
- [#141](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/141) includes an agent credential dependency. Review all enabled beta paths before invitations; schedule a separate agent review when it ships, rather than omit the beta review.
- [#146](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/146) depends on agent privacy and billing work. Split the beta data/retention/deletion obligations from future agent/billing additions if those features are deferred.
- [#148](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/148) requires no unresolved P0 launch blockers. A beta-specific checklist or explicitly revised release scope is needed; this document grants no exception to that launch gate.

Each implementation issue should name its requirement ID(s), release slice, user-visible acceptance evidence, and dependencies. Adding a new MVP capability requires updating this document's boundary, acceptance scenarios, and traceability together. A deferred requirement must not slip into MVP solely because its UI looks convenient to build, and a necessary privacy/reliability prerequisite must not slip out merely because its parent epic also contains later work.
