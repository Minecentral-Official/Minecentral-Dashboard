# MineCentral v1 feature and data inventory

Audit date: 2026-09-24. Source baseline: `05c4456a230802b1c7b970f4a17e093209753652`.

Addresses [issue #18](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/18), under [epic #2](https://github.com/Minecentral-Official/Minecentral-Dashboard/issues/2).

This is a source-code inventory, not a production database audit or runtime certification. The working tree was clean when inspected. No production records, external storage, provider dashboards, or deployed configuration were inspected. Dispositions below are the recommended baseline for subsequent v2 work; they do not authorize deletion or implement migration. The parent epic's direction is to help owners assemble, configure, troubleshoot, and maintain server stacks. This audit preserves useful foundations without treating the existing download directory or public server listing as the entire v2 product.

## Disposition vocabulary

- **Keep:** retain the capability or reusable foundation.
- **Refactor:** retain the capability, but change its implementation or contract before relying on it in v2.
- **Migrate:** preserve durable data and relationships with a verified mapping to the eventual v2 schema.
- **Archive:** retain historical code, records, or design context outside the active v2 experience until needed.
- **Remove:** retire an obsolete or empty surface after checking consumers; this does not mean deleting user data.

Code and data can have different dispositions. A refactored feature can require all its records to migrate.

## Current flows and trust boundaries

### Authentication and authorization

`/sign-in` offers Discord and GitHub through the Better Auth client. `/api/auth/[...all]` delegates GET/POST to Better Auth with the Drizzle adapter. The server enables the admin plugin and trusts `minecentral.net` and `www.minecentral.net`. Email/password login is not enabled by this configuration, although the account table has a password field.

The `(authorized)` layout redirects guests to `/sign-in`; `(unauthorized)` redirects signed-in users to `/dashboard`; the admin layout checks `validateRole('admin')`. `validateSession()` throws without a session; `validateRole()` returns a boolean. Resource edit helpers permit owners or admins; server edit helpers permit owners only. Sign-out uses the auth client. Preserve provider/user ID mappings and bans; do not assume a new auth system can safely relink accounts by email alone. Source: [server config](../../src/lib/auth/configs/auth.server.ts), [helpers](../../src/lib/auth/helpers), [authorized layout](<../../src/app/(authorized)/layout.tsx>).

### Resource/plugin lifecycle

1. A signed-in user creates a resource with title, subtitle, slug, and type. The resource starts as `draft`; an activity record is added.
2. The dashboard edits general fields, markdown description, categories/languages, external links, and icon. UploadThing accepts owner-uploaded icons (256 KB) and JAR/ZIP releases (16 MB). The browser analyzer can populate release metadata; the upload callback writes the release and file URL.
3. The UI readiness helper requires a release and description. Publishing sets `pending` for an owner and `accepted` for an admin. `rejected` exists in the schema, but no dedicated rejection workflow was found. The publish action does not itself call the readiness helper.
4. `/plugins` queries accepted resources by type, text/author, category, loader, and game version. Other resource-type discovery pages are placeholders. Sort UI exists, but the API/query use updated-time ordering rather than applying that selection. Release filtering occurs partly after pagination.
5. Detail/version pages show author, compatibility, links, likes, and downloads. Likes are user/resource pairs. Download requests increment a release counter and redirect to external storage. The release table links send a numeric release ID, but the download lookup filters `pluginId` (resource ID), so this contract is inconsistent.
6. Deletion deletes the parent resource directly. Release FKs have no cascade; files are not deleted by this mutation. Preserve releases and storage before designing deletion/migration.

Evidence: [actions](../../src/features/resources/actions), [upload callbacks](../../src/features/resources/uploadthing), [publish readiness](../../src/features/resources/queries/project-can-publish.boolean.ts), [filtered query](../../src/features/resources/queries/resource-list-all-filter.get.ts), [download lookup](../../src/features/resources/queries/release-by-download-id.get.ts), [release links](../../src/features/resources/components/resource/table/table-project-releases.tsx).

### Server-list and vote lifecycle

1. A signed-in owner creates a draft listing with title, slug, address, and port. The configurable per-user limit defaults to five. Case-insensitive slug and address/port uniqueness have database indexes; the per-user count check is application-side.
2. The owner edits profile fields and uploads a banner into the field named `iconUrl`. Publishing requires title, slug, address, port, description, category, platform, and banner. Incomplete edits or banner removal can move a published listing back to draft. Deletion requires typing the listing title.
3. `/serverlist` accepts `q`, comma-separated `category`/`platform`, `sort`, `p`, and `limit`; filters use OR within each array and AND across dimensions. Ordering is updated, newest, or all-time vote count. List queries enforce publication plus readiness conditions. Detail queries enforce published status, but do not repeat the entire readiness check. Public DTOs expose only Votifier enabled state/server ID, not connection configuration.
4. Voting allows guests. A year-lived HTTP-only cookie identifies the voter; SHA-256 hashes of IP and user agent provide a fallback identity pair. A signed-in user ID is optional attribution, not the cooldown key. The check uses each listing's cooldown (default 24 hours). A Minecraft username is required only when Votifier rewards are enabled.
5. The vote is stored first, then the request awaits TCP Votifier delivery and updates `sent`/`failed`; a failed delivery still leaves the vote counted. There is no durable queue or retry worker. Deleting a listing cascades votes and Votifier configuration.

Evidence: [server actions](../../src/features/serverlist/actions), [public query](../../src/features/serverlist/queries/server-list-all-filter.get.ts), [detail query](../../src/features/serverlist/queries/server-by-slug.get.ts), [readiness](../../src/features/serverlist/util/server-public-ready.ts), [vote action](../../src/features/serverlist/actions/vote-for-server.action.ts), [TCP delivery](../../src/features/serverlist/votifier/send-vote.tsx).

### Tickets, admin, and activity

Ticket creation transactionally inserts the ticket and initial message, then records activity. Categories are server issues, billing, plugin support, and general inquiry. Status is `open`, `in-progress`, or `closed`. User lists are scoped to the current user; single-ticket reads allow owner/admin. Replies can change an open ticket to in-progress when authored by someone other than its owner. Status changes currently require ownership, even for admins. There is no dedicated admin ticket queue route.

The reply action checks authentication and ticket existence but does not require owner/admin membership. The standalone messages query also lacks its own authorization check. These boundaries need refactoring before reuse; protected display routes alone do not enforce action permissions. Admin resource listing uses an API that has no corresponding role guard. Activity is free-text history tied to users, not a structured audit-event model.

Evidence: [ticket queries](../../src/features/tickets/queries), [ticket mutations](../../src/features/tickets/mutations), [admin resource API](../../src/app/api/resources/all/route.ts), [activity writer](../../src/lib/activity/mutations/activity.add.ts).

Except for the explicit cascades/set-null above, FKs do not declare a delete action. User deletion or parent removal can therefore be blocked by dependents. Preserve original IDs where possible; otherwise keep durable old-to-new mappings for every FK, external reference, and public URL. Restore identity sequences above migrated maximum IDs. Auth timestamps, date-only ticket creation, and timezone-aware domain timestamps have different precision/semantics and must not be silently normalized to fabricated values.

External durable assets also matter: UploadThing release binaries, resource icons and server banners; user avatars that may be provider-hosted; OAuth application configuration; and any Stripe customer/subscription records. A database backup alone does not preserve file bytes or provider-side state. Keep file inventories and URL mappings, verify accessibility/checksums during an eventual migration, and retain unpublished uploads. There are no tables for collections, saved servers, worlds, stack definitions, or hosted server instances in this snapshot.

## Migration preservation checklist for subsequent implementation

1. Snapshot the deployed schema, data, file inventory, and external provider references; record source version and row counts without putting credentials or personal records in the repository.
2. Define the destination model and a disposition/mapping for every table above. Preserve ownership, unpublished work, moderation status, support messages, vote history, customer IDs, and all externally referenced IDs/URLs. Resolve auth session/verification policy explicitly.
3. Rehearse on a copy. Check row counts by status/type, FK integrity, case-insensitive slug collisions, duplicate customer mappings, file checksums/accessibility, timestamp precision, and identity sequence values.
4. Validate representative guest/owner/admin flows, private-data boundaries, old public URLs, release downloads, and login/provider links against the migrated copy. Reconcile counters from raw preserved data, not current display aggregates.
5. Plan cutover writes/deltas, cache invalidation, rollback, and vote-delivery deduplication. Only retire old storage or records after reconciliation and a separately defined retention decision.

The v2 navigation, final product objects, detailed migration implementation, and fixes identified here belong to subsequent work under epic #2. No runtime code, database schema, or external application state is changed by this audit.
